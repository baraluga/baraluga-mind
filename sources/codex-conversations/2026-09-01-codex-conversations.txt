## What Brian Actually Looks For

Brian is not hiring a framework user — he's hiring a **quality multiplier**: someone who raises the engineering floor of any team they join. Technology choice is irrelevant; habits are everything.

### Engineering habits (primary signal)

When assessing a take-home, always check for these — they are more important than the functional output:

- **Commit hygiene** — conventional commits (feat/fix/chore/etc.) + micro commits. One giant "initial commit" is a red flag.
- **Commit grouping** — are commits sliced vertically by feature/concern, or arbitrarily dumped? Vertical slicing shows systems thinking.
- **Tests** — 100% coverage + TDD is ideal; partial coverage is acceptable; **zero tests is unacceptable** at L3.
- **CI/CD** — bonus points for setting this up even when not asked. Shows initiative and production mindset.
- **Git hooks** — pre-commit hooks (linting, formatting, test gates) even on a solo repo signal discipline.
- **Linting / formatting** — a configured linter (flake8, pylint, black, eslint, etc.) is expected at this level.

### Take-Home Assessment Criteria

- **Judging approach**: holistic, not rubric-based — one written assessment per candidate
- **Hold the L3 bar** regardless of the 4–6 hour time constraint; the choices candidates make under pressure reveal their judgment
- **Advancement**: case-by-case, Brian decides — no hard cutoffs
- **Code quality first**, written explanation (README) is secondary but noted if absent or weak
- **Bonus (Part 2 — AI Agent)**: pure upside only — skipping it doesn't count against the candidate; if attempted, what matters is that it's grounded and explainable
- **Reproducibility**: notable but not fatal — flag it, but don't let it overshadow a well-structured solution
- **AI assistance**: neutral — transparency matters; probe understanding in the walkthrough

### Assessment output format

### Assistant - 2026-09-01T11:56:46.662Z

Hindi ka mali. What we built is technically a Grafana drill-down, but it’s the most basic kind: a context-aware hyperlink.

Grafana data links are primarily sold as:

> Click a series/data point → navigate somewhere more specific while carrying the time range, variables, labels, or selected value.

They are not an embedded expansion, modal, drawer, or nested dashboard. Grafana explicitly distinguishes:

- Dashboard links — navigation from the dashboard header.
- Panel links — navigation from the panel menu/title.
- Data links — navigation after clicking a particular series or measurement.

That’s exactly how [Grafana documents dashboard and panel navigation](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/manage-dashboard-links/) and [data links](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/configure-data-links/).

So yes: what you saw is the native feature behaving as intended.

Why it feels underwhelming
--------------------------

Because the word “drill-down” suggests progressive disclosure:

```text
Overview
  └─ click DAM
       └─ detail appears here, in context
```

But basic Grafana data links behave like:

```text
Overview
  └─ click DAM
       └─ navigate to another dashboard URL
```

Our POC adds value by carrying `National`, `DAM`, `Price`, and the time range. But visually, it is still just dashboard-to-dashboard navigation. The destination replacing the source in the same tab makes the context switch especially noticeable.

Grafana’s expected usage
------------------------

The normal pattern is:

1. Start on a stable overview dashboard.
2. Notice an interesting series or value.
3. Click it.
4. Open a purpose-built detail dashboard with the relevant filters already applied.
5. Use browser Back—or a manually supplied “Back to overview” link—to return.

Typical examples are service overview → service detail, fleet → host, region → market, or alert → logs/traces.

Grafana also has products called “Drilldown” apps for metrics, logs, traces, and profiles. Those offer a more guided, point-and-click exploratory experience. But they are specialized observability experiences—not a generic system for embedding one arbitrary Athena-backed dashboard inside another.

What would feel better for SMP?
-------------------------------

There are three realistic levels:

1. Small improvement: open in a new tab

   Set `targetBlank: true`. The overview remains open, and the investigation appears beside it. This is probably the best immediate improvement, but it still isn’t embedded.

2. Better native dashboard UX: overview and detail on one dashboard

   Put the summary panels at the top and detailed panels below, all driven by shared variables. Clicking or selecting a market updates the lower detail section. This feels much more like an embedded drill-down, although it requires redesigning the dashboard rather than merely adding links.

3. True exploratory application

   Build a custom Grafana app/Scenes experience with breadcrumbs, tabs, drawers, or contextual panels. That can deliver the interaction you expected, but it is no longer a “small Grafana dashboard POC.”

My honest assessment: the current result proves the navigation and context-propagation capability, but it’s not a compelling product demo. For SCR-1248, I’d describe it as a tracer bullet—not the finished drill-down experience.

The most sensible next iteration is either:

- switch the link to a new tab and add a clear return path; or
- redesign Expanded as a unified overview + detail dashboard, which is the closest native Grafana equivalent to the embedded interaction you expected.
