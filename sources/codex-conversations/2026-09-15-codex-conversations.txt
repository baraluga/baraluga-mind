## Repository map

- `app.py`, `layout.py`, and `callbacks.py` are the Dash entry point, shared
  layout, and callback/data behavior.
- `components/` contains reusable UI components.
- `data/` contains sample data and real-data loading logic.
- `assets/` contains CSS, JavaScript, images, and flags.
- `tests/` contains the pytest suite.
- `data_pipeline/scripts/` contains the tracked refresh orchestrator and
  transforms; `data_pipeline/experiments/` and `archive/` are not automatically

- `deploy.ps1` is the Windows/DAC deployment helper; it is not part of CI.
- `deployment/runtime/` is the versioned DAC runtime overlay. CI
  packages a Git commit with sample data only after tests pass; there is no
  automated deployment job. See `deployment/README.md` and `docs/atlas-cd-handoff.md`.

## Verified commands

For local development run `python3.12 scripts/dev.py setup` (Windows:
`py -3.12 scripts/dev.py setup`). This installs and verifies Git hooks.
Use `scripts/dev.py hooks` to diagnose missing hooks; do not bypass or remove
hooks to make a commit or push pass. Run `python3.12 scripts/dev.py check` for
all checks using the managed `.venv`. CI uses the direct commands below:

```bash
python -m pip install -r requirements-dev.txt
python -m ruff check .
python -m ruff format --check .
python -m pytest
```

`pytest` enforces a 20% coverage floor for
`callbacks.py` and `data/real_data.py`. Preserve that gate and add focused
tests for deliberate behavior changes.

## Change discipline

- Preserve data semantics, especially labels, units, periods, ownership,
  committed-versus-realized categories, and workbook sheet meanings.
- Do not rewrite or reformat unrelated files. Review the final diff and keep
  generated data, reports, credentials, and other environment-owned artifacts
  out of Git.
- For notebook or pipeline edits, preserve notebook metadata and outputs when
  possible, inspect the changed cells, and add a narrow regression test when a
  behavior or schema assumption changes.
- The app can use tracked sample data, but real refresh inputs under
  `data_pipeline/inbox/` and `data/raw/` are ignored and environment-owned.
  Do not invent missing inputs or run a publish step to work around them.

## Deployment boundary

GitHub Actions validates pushes and pull requests. A green CI run does not
deploy anything. Deployment belongs to the explicit Windows/DAC workflow in
`deploy.ps1`, which requires the sibling deployment repository, DAC profiles,
service configuration, and environment-owned data/authentication. Keep that
boundary intact unless the user explicitly asks for deployment work.

For the normal solo edit/format/lint/test/commit/push workflow, see
`CONTRIBUTING.md`.

**My recommendation: a short user story, a little context, and testable acceptance criteria.** Add constraints and scope boundaries only when they matter.

The science supports useful quality checks; it doesn’t establish one universally superior ticket template. So: evidence-informed, with a modest amount of agile ceremony lol.

## What the evidence actually says

- **Research:** The *Quality User Story* framework identifies qualities such as one feature per story, unambiguous wording, a meaningful rationale, and explicit dependencies. It draws on real industry stories, but doesn’t prove that a particular sentence structure produces better delivery outcomes. [Lucassen et al., 2015](https://research-portal.uu.nl/ws/portalfiles/portal/228920794/Forging_high-quality_User_Stories_Towards_a_discipline_for_Agile_Requirements.pdf)
- **Industry guidance:** “As a … I want … so that …” is a useful reminder to capture **who, what, and why**. Agile Alliance explicitly treats it as training wheels and says relaxed phrasing can work equally well. [Agile Alliance](https://agilealliance.org/glossary/user-story-template/)
- **The working practice:** Stories need discussion and agreement about acceptance—the familiar **card, conversation, confirmation**. The written ticket supports that collaboration. [Agile Alliance](https://agilealliance.org/user-story-conversations/)

## The format I’d use

```markdown
## Title
[Short description of the user’s goal]

## Story
As a [specific user/role],
I want to [achieve a goal],
so that [meaningful benefit].

## Context
[Why this matters; relevant current behavior or evidence.
Skip if the story already makes this clear.]

## Acceptance criteria
- [Observable successful behavior]
- [Relevant business rule or boundary]
- [Important failure or empty-state behavior]

## Constraints / out of scope — if needed
[Required limits, dependencies, or explicit exclusions]

## References — if needed
[Designs, supporting evidence, technical discussion]
```

That’s my synthesis, not a research-validated mandatory template.

### Example

**Title:** Export filtered invoices to CSV

**Story:**  
As a finance analyst, I want to export the invoices matching my current filters so that I can reconcile them without manually copying records.

**Context:**  
Analysts currently copy invoice details from multiple pages of search results.

**Acceptance criteria:**

- The export includes all matching invoices across all result pages.
- Columns are invoice number, customer, issue date, currency, and total.
- The export includes only invoices the analyst has permission to view.
- When no invoices match, export is unavailable and the page explains why.

**Out of scope:**  
Scheduled exports and additional file formats.

## A few rules that make it work

1. **Make the benefit meaningful.** “So that I can export invoices” just repeats the feature.
2. **Describe observable outcomes.** Someone should be able to determine whether each criterion passes.
3. **Use Given/When/Then when conditions matter.** It expresses starting state → action → outcome. Simple criteria can stay as bullets. [Cucumber reference](https://cucumber.io/docs/gherkin/reference/)
4. **Keep each story small enough to deliver and verify.** Split distinct goals before adding more sections.
5. **Let technical work use an appropriate format.** Scrum doesn’t require every backlog item to be a user story. [Scrum Guide](https://scrumguides.org/scrum-guide.html#product-backlog)

**The practical quality test: can product, engineering, and QA read it and agree on who benefits, what changes, and how they’ll verify it?**

**They fit together. A BDD-style story keeps the user goal and adds concrete examples of expected behavior.** The biggest change is how the team discovers and verifies those examples.

BDD—*Behavior-Driven Development*—involves discussing examples together, agreeing on them, then using automated examples to guide implementation. Writing Given/When/Then alone covers only part of that process. [Cucumber’s BDD guide](https://cucumber.io/docs/bdd/)

## How the formats compare

| Part | Format I suggested | BDD-style version |
|---|---|---|
| User goal | As a… I want… so that… | Same |
| Context | Why this matters | Same |
| Acceptance criteria | Observable rules, usually bullets | Rules supported by concrete scenarios |
| Examples | Included when useful | Central to discovering and defining behavior |
| Verification | Criteria guide testing | Selected scenarios become automated checks |
| Collaboration | Discuss and refine the story | Product, engineering, and testing perspectives explore examples together |

Both can be rigorous. BDD makes the examples and feedback loop more explicit. [BDD practices](https://cucumber.io/docs/bdd/)

## Same story, expressed with BDD

**Story**

> As a finance analyst, I want to export invoices matching my current filters so that I can reconcile them without manually copying records.

**Acceptance rule**

> Export all matching invoices across all result pages.

**Scenario illustrating that rule**

```gherkin
Scenario: Export results spanning multiple pages
  Given 75 invoices match my current filters
  And the results page displays 25 invoices at a time
  When I export the filtered invoices
  Then the CSV contains all 75 matching invoices
  And it contains no non-matching invoices
```

**Another acceptance rule**

> Export only invoices the analyst is permitted to view.

```gherkin
Scenario: Exclude invoices outside my access
  Given invoice A matches my filters and I can view it
  And invoice B matches my filters but I cannot view it
  When I export the filtered invoices
  Then the CSV includes invoice A
  And it excludes invoice B
```

**The rule states the requirement; the scenario gives a concrete example of what satisfying it means.** Gherkin supports this relationship directly through `Rule` and `Scenario`. [Gherkin reference](https://cucumber.io/docs/gherkin/reference/)

## Which would I use?

My recommendation is a **lightweight hybrid**:

1. **Story:** who, goal, benefit.
2. **Acceptance rules:** short, readable bullets.
3. **Examples:** Given/When/Then for conditions, permissions, calculations, state changes, and important edge cases.
4. **Constraints and open questions:** only where needed.

For something simple, bullets may communicate everything. For behavior with multiple conditions, concrete examples often expose questions that a broad criterion hides.

And I’d qualify my earlier science answer: **the sources here support BDD as an established practice; they don’t establish that Given/When/Then universally outperforms clear bullets.** I’d choose it when the examples improve shared understanding and can help verify the implementation.
