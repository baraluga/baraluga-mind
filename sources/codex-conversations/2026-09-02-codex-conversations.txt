## Current Repos

| Repo | Purpose | Tooling |
|---|---|---|
| `scraper-scripts` | Raw standalone scraper scripts and behavioral references before Airflow adaptation | Python 3.13, `uv` |
| `smp-india` | India-owned Airflow DAGs split from the former `scraper-dags` repo | Python 3.13, Airflow 3.x, `uv` |
| `smp-japan` | Japan-owned Airflow DAGs split from the former `scraper-dags` repo | Python 3.13, Airflow 3.x, `uv` |
| `smp-tool` | Airflow Docker image, Helm values, Kubernetes scripts, Okta auth, Minikube/EKS setup | Python 3.12, `uv`, Helm, Kubernetes |
| `smp-dashboard` | Grafana dashboards and `cdh-dataset-manager` for CommonDataHub datasets | Python 3.11, `uv` |
| `apac-tsdb-scraper` | Poetry/solaris-sfw TSDB scrapers deployed through the older Lambda/tag flow | Python 3.12, Poetry |

Legacy names still appear in older docs and code comments:

- `scraper-dags` is now split into `smp-india` and `smp-japan`.
- `scraper-tool` is now `smp-tool`.
- `scraper-dashboard` is now `smp-dashboard`.

## End-to-End SMP Flow

```text
scraper-scripts  ->  smp-india / smp-japan  ->  smp-tool  ->  smp-dashboard
(reference impl)     (Airflow DAGs)             (runtime)     (CDH + Grafana)
```

Use `scraper-scripts` as the behavioral source when porting or validating a DAG. Region-specific DAG implementation now belongs in either `smp-india` or `smp-japan`; shared Airflow/platform behavior should come from `smp-common` or `smp-tool`, not be copied between region repos.

## Shared Rules

- Do not commit credentials, tokens, kubeconfigs, generated local secrets, or one-off path rewrites.
- Private dependencies come from ENGIE Artifactory. Prefer fixing local credentials over changing package indexes.
- Keep region boundaries explicit: India DAG code in `smp-india`, Japan DAG code in `smp-japan`.
- For Airflow DAGs, keep heavy imports out of module scope because Airflow parses DAG files frequently.
- For dashboard work, verify the upstream parquet/S3/CDH shape before changing Grafana JSON or dataset definitions.
- For infra changes, call out whether the change affects image build, Helm values, auth, DAG sync, runtime secrets, or Kubernetes namespaces.

## Cross-Repo Workflow: Porting A Script To A DAG

1. Run and observe the source script in `scraper-scripts`; capture inputs, outputs, credentials, file names, date logic, and failure behavior.
2. Choose the DAG repo by market ownership: `smp-india` or `smp-japan`.
3. Check whether an existing DAG for the same source should be extended before creating a new DAG.
4. Implement under `dags/src/`, keeping task runtime scraper modules under `dags/src/scripts/`.
5. Validate locally with `ruff`, `pytest`, and, when practical, `airflow dags test`.
6. Coordinate deployment through the appropriate branch/environment and `smp-tool` git-sync/Helm configuration.
7. Update `smp-dashboard` only after the DAG output is stable and visible where CDH/Grafana expects it.

## Branch And Environment Notes

- GitHub repos commonly use `main`; some DAG deployment flows still reference `dev`, `qa`, `master`, or region-specific branches.
- `smp-tool` has region-aware config under `config/japan/<env>/` and `config/india/<env>/`.
- Airflow namespaces are region-specific in current scripts, for example `smp-dev`, `smp-qa`, `smp-prod`, `smp-india-dev`, `smp-india-qa`, and `smp-india-prod`.
- Treat any old `scraper-dags`/ADO git-sync reference as potentially stale and verify against current `smp-tool` config before editing deployment behavior.

WITH prices AS (
  SELECT
    CAST(
      with_timezone(CAST(application_date AS timestamp), 'UTC')
        AT TIME ZONE 'Asia/Kolkata'
      AS timestamp
    ) AS time_ist,
    value / 1000 AS price_rupees_per_kwh

    AND metric = 'price'
    AND market = 'DAM'

  SELECT
    year(time_ist) AS delivery_year,
    month(time_ist) AS delivery_month,

    price_rupees_per_kwh
  FROM prices
)

  delivery_year,
  CASE band
    WHEN 0 THEN '00:00 - 04:00'
    WHEN 1 THEN '04:00 - 08:00'
    WHEN 2 THEN '08:00 - 12:00'
    WHEN 3 THEN '12:00 - 16:00'
    WHEN 4 THEN '16:00 - 20:00'
    WHEN 5 THEN '20:00 - 24:00'

  round(avg(CASE WHEN delivery_month = 2  THEN price_rupees_per_kwh END), 2) AS feb,

  round(avg(CASE WHEN delivery_month = 4  THEN price_rupees_per_kwh END), 2) AS apr,
  round(avg(CASE WHEN delivery_month = 5  THEN price_rupees_per_kwh END), 2) AS may,
  round(avg(CASE WHEN delivery_month = 6  THEN price_rupees_per_kwh END), 2) AS jun,
  round(avg(CASE WHEN delivery_month = 7  THEN price_rupees_per_kwh END), 2) AS jul,
  round(avg(CASE WHEN delivery_month = 8  THEN price_rupees_per_kwh END), 2) AS aug,
  round(avg(CASE WHEN delivery_month = 9  THEN price_rupees_per_kwh END), 2) AS sep,
  round(avg(CASE WHEN delivery_month = 10 THEN price_rupees_per_kwh END), 2) AS oct,
  round(avg(CASE WHEN delivery_month = 11 THEN price_rupees_per_kwh END), 2) AS nov,
  round(avg(CASE WHEN delivery_month = 12 THEN price_rupees_per_kwh END), 2) AS dec

ORDER BY delivery_year, band

### User - 2026-09-02T09:00:16.576Z

what's the mental mindset for a project to run scrum vs kanban, in the first place?

### Assistant - 2026-09-02T09:00:37.381Z

The fundamental difference is the kind of promise the team believes it can responsibly make.

| Scrum mindset | Kanban mindset |
|---|---|
| “We can choose a coherent goal and protect it for the next sprint.” | “Demand and capacity vary, so we will continuously choose the most valuable work.” |
| Optimise around a **timeboxed goal** | Optimise around **flow of individual work items** |
| Change is mostly absorbed between sprints | Change is expected at any time, but governed by explicit rules |
| The team is reasonably stable and dedicated | People or capacity may be shared and variable |
| Most work can be made ready before commitment | Work frequently depends on uncertain inputs or external parties |
| Success means achieving the Sprint Goal | Success means delivering reliably with short, predictable cycle time |
| Planning asks, “What can we accomplish together?” | Replenishment asks, “What should we pull next?” |
| Protect the sprint from interruption | Control interruptions and their cost |
| Inspect progress at sprint boundaries | Inspect and improve flow continuously |

### Choose Scrum when

The team can honestly say:

> “For the next two weeks, we have a stable team, a clear product goal, sufficiently understood work, and the authority to protect that goal.”

Typical conditions:

- A dedicated cross-functional product team
- One empowered Product Owner
- A meaningful increment can be produced each sprint
- Dependencies can usually be resolved before planning
- Stakeholders accept that new requests normally wait for the next sprint
- The work benefits from everyone pursuing one shared outcome

Scrum is fundamentally a **focus and learning system**. The sprint is a protected experiment: choose a goal, build something, inspect the result, and adapt.

### Choose Kanban when

The team can more honestly say:

> “We cannot predict exactly what will arrive or unblock next, but we can control how much we start and how efficiently it flows.”

Typical conditions:

- Support, maintenance, incidents, or request-driven work
- Changing priorities
- Shared or fluctuating team capacity
- Many external approvals and dependencies
- Work items are relatively independent
- Releases happen continuously
- Stakeholders care more about response time than sprint goals

Kanban is fundamentally a **flow and service-management system**. It doesn’t try to freeze demand; it makes demand, capacity, queues, and delay visible and manageable.

### The diagnostic question

Don’t begin with ceremonies. Ask:

> **Is our main coordination problem protecting focus around a shared goal, or managing unpredictable flow?**

- If the main problem is **lack of focus despite reasonably predictable work**, Scrum helps.
- If the main problem is **queues, blockers, interruptions, and variable demand**, Kanban helps.
- If you need focused checkpoints but work behaves unpredictably between them, Scrumban is often the practical fit.

For SMP, the mindset appears to be:

> “We can agree on priorities periodically, but we cannot honestly guarantee that stakeholder inputs, access, approvals, budgets, and production issues will cooperate with the sprint boundary.”

That’s why Scrumban fits: **forecast at the cadence, commit only when pulling ready work, and optimise for finishing rather than keeping the sprint plan cosmetically intact.**
