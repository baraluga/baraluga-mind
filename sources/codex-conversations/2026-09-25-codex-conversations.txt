Flags take a value: `--flag value`, or `--flag=value`. Use the `=` form when the value itself

For the task where this skill is invoked, explicitly use subagents if and only if the criteria below are met. Invocation authorizes that decision without another confirmation; it does not require delegation or expand the user's task or permissions.

## Decide whether to delegate

Delegate only when all of these are true:

- There is a concrete, bounded subtask with a clear deliverable that can run independently.
- The main agent has useful work to do alongside it, rather than immediately waiting for its result.
- The expected time savings or improvement in quality outweigh briefing, coordination, and review costs.
- Responsibilities can be separated to avoid conflicting edits and unnecessary duplicate work.

Good candidates include investigating independent components, comparing distinct approaches, or requesting a focused second opinion while continuing implementation or validation. An independent review may intentionally overlap in subject matter when a second assessment adds value.

Stay solo for small changes, tightly sequential work, or subtasks that require nearly continuous shared context. Using zero subagents is a valid outcome. Do not split work just to demonstrate delegation.

Review returned findings and changes before relying on them, reconcile disagreements, and perform verification appropriate to the combined result. # Parallel When Useful

For the task where this skill is invoked, explicitly use subagents if and only if the criteria below are met. Invocation authorizes that decision without another confirmation; it does not require delegation or expand the user's task or permissions.

## Decide whether to delegate

Delegate only when all of these are true:

- There is a concrete, bounded subtask with a clear deliverable that can run independently.
- The main agent has useful work to do alongside it, rather than immediately waiting for its result.
- The expected time savings or improvement in quality outweigh briefing, coordination, and review costs.
- Responsibilities can be separated to avoid conflicting edits and unnecessary duplicate work.

Good candidates include investigating independent components, comparing distinct approaches, or requesting a focused second opinion while continuing implementation or validation. An independent review may intentionally overlap in subject matter when a second assessment adds value.

Stay solo for small changes, tightly sequential work, or subtasks that require nearly continuous shared context. Using zero subagents is a valid outcome. Do not split work just to demonstrate delegation.

## Delegate with clear ownership

Use the available subagent tools within the current task. This skill does not request separate sidebar tasks. Choose the smallest useful number of agents within available limits.

Brief each agent with its objective, necessary context, permitted scope, expected result, and any file ownership boundaries. Keep integration and the final response with the main agent, and continue useful local work while agents run.

Review returned findings and changes before relying on them, reconcile disagreements, and perform verification appropriate to the combined result. End or redirect delegated work when it becomes redundant or no longer helps. Explain delegation briefly when it matters to the user's understanding; do not add a ceremony for deciding to stay solo.

</skill>

# Parallel When Useful

For the task where this skill is invoked, explicitly use subagents if and only if the criteria below are met. Invocation authorizes that decision without another confirmation; it does not require delegation or expand the user's task or permissions.

## Decide whether to delegate

Delegate only when all of these are true:

- There is a concrete, bounded subtask with a clear deliverable that can run independently.
- The main agent has useful work to do alongside it, rather than immediately waiting for its result.
- The expected time savings or improvement in quality outweigh briefing, coordination, and review costs.
- Responsibilities can be separated to avoid conflicting edits and unnecessary duplicate work.

Good candidates include investigating independent components, comparing distinct approaches, or requesting a focused second opinion while continuing implementation or validation. An independent review may intentionally overlap in subject matter when a second assessment adds value.

Stay solo for small changes, tightly sequential work, or subtasks that require nearly continuous shared context. Using zero subagents is a valid outcome. Do not split work just to demonstrate delegation.

## Delegate with clear ownership

Use the available subagent tools within the current task. This skill does not request separate sidebar tasks. Choose the smallest useful number of agents within available limits.

Brief each agent with its objective, necessary context, permitted scope, expected result, and any file ownership boundaries. Keep integration and the final response with the main agent, and continue useful local work while agents run.

Review returned findings and changes before relying on them, reconcile disagreements, and perform verification appropriate to the combined result. End or redirect delegated work when it becomes redundant or no longer helps. Explain delegation briefly when it matters to the user's understanding; do not add a ceremony for deciding to stay solo.

</skill>

# Parallel When Useful

For the task where this skill is invoked, explicitly use subagents if and only if the criteria below are met. Invocation authorizes that decision without another confirmation; it does not require delegation or expand the user's task or permissions.

## Decide whether to delegate

Delegate only when all of these are true:

- There is a concrete, bounded subtask with a clear deliverable that can run independently.
- The main agent has useful work to do alongside it, rather than immediately waiting for its result.
- The expected time savings or improvement in quality outweigh briefing, coordination, and review costs.
- Responsibilities can be separated to avoid conflicting edits and unnecessary duplicate work.

Good candidates include investigating independent components, comparing distinct approaches, or requesting a focused second opinion while continuing implementation or validation. An independent review may intentionally overlap in subject matter when a second assessment adds value.

Stay solo for small changes, tightly sequential work, or subtasks that require nearly continuous shared context. Using zero subagents is a valid outcome. Do not split work just to demonstrate delegation.

# User Story

Use Brian's agreed default: a concise user goal, observable acceptance rules, and concrete BDD examples where they clarify behavior. Keep the structure consistent across tools while scaling detail to the work. Follow explicit user or project template requirements when they differ.

## Writing workflow

- Use the request and available source material to identify the actor, goal, benefit, current problem, and known rules. When editing an existing ticket, read its current content first and preserve relevant decisions and references.
- Apply `brian-voice` when available for Brian's authored content. Keep stories direct, concise, and free of corporate padding; this skill supplies the story structure.
- Aim for one coherent user outcome that can be delivered and verified. If it contains distinct outcomes, propose or draft smaller stories as appropriate; do not create additional external tickets unless authorized.
- Do not invent business rules, numerical limits, permissions, user research, or product decisions. Ask about material unknowns while drafting what is known, or record them as open questions. Label proposed behavior clearly; never present assumptions as agreed acceptance criteria.
- Do not force bugs, spikes, infrastructure tasks, or other technical work into fictional user personas. Use a problem, desired outcome, and verification format when a user story is inappropriate.
- For bug reports, use `bug-report` when available.

## Default format

Use this order. Title, Story, and Acceptance criteria are the core; include other sections only when useful and omit empty headings.

```markdown
# [Short title describing the user's goal]

## Story
As a [specific role], I want to [achieve a goal], so that [meaningful benefit].

## Context
[Brief current problem, reason for the change, or supporting evidence.]

## Acceptance criteria
- [Observable behavior or business rule.]
- [Relevant boundary or failure behavior.]

## Examples
[Named Given/When/Then scenarios for rules that benefit from examples.]

## Constraints / out of scope
[Known constraints, dependencies, and meaningful scope boundaries.]

## Open questions
[Unresolved decisions that affect behavior or scope.]

## References
[Relevant designs, evidence, related work, or technical discussion.]
```

The story captures who, what, and why. Use a real benefit rather than repeating the feature. Natural phrasing is acceptable when clearer than the sentence template. Keep implementation plans separate from the user goal; include necessary technical constraints without prematurely prescribing a solution.

## Acceptance rules and BDD examples

- Write acceptance criteria as short, observable rules with an objective pass/fail interpretation. Cover relevant happy paths, boundaries, permissions, and failures in proportion to the feature; do not add speculative scope or a fixed quota of criteria.
- Retain general rules even when examples illustrate them. One concrete scenario does not fully specify a general rule.
- Add Given/When/Then scenarios when conditions, permissions, calculations, state changes, or edge cases need clarification. Simple stories can use bullets alone. Do not mechanically translate every bullet into repetitive Gherkin.
- Name each scenario by the behavior it illustrates. Given establishes context, When identifies the trigger, and Then states observable results. Use concrete values that clarify a rule; illustrative fixture values must not introduce new requirements.
- Describe domain behavior rather than click-by-click scripts, CSS selectors, API internals, or database assertions unless those details are themselves part of the requested contract. Prefer one meaningful trigger per scenario.

# User Story

Use Brian's agreed default: a concise user goal, observable acceptance rules, and concrete BDD examples where they clarify behavior. Keep the structure consistent across tools while scaling detail to the work. Follow explicit user or project template requirements when they differ.

## Writing workflow

- Use the request and available source material to identify the actor, goal, benefit, current problem, and known rules. When editing an existing ticket, read its current content first and preserve relevant decisions and references.
- Apply `brian-voice` when available for Brian's authored content. Keep stories direct, concise, and free of corporate padding; this skill supplies the story structure.
- Aim for one coherent user outcome that can be delivered and verified. If it contains distinct outcomes, propose or draft smaller stories as appropriate; do not create additional external tickets unless authorized.
- Do not invent business rules, numerical limits, permissions, user research, or product decisions. Ask about material unknowns while drafting what is known, or record them as open questions. Label proposed behavior clearly; never present assumptions as agreed acceptance criteria.
- Do not force bugs, spikes, infrastructure tasks, or other technical work into fictional user personas. Use a problem, desired outcome, and verification format when a user story is inappropriate.
- For bug reports, use `bug-report` when available.

## Default format

Use this order. Title, Story, and Acceptance criteria are the core; include other sections only when useful and omit empty headings.

```markdown
# [Short title describing the user's goal]

## Story
As a [specific role], I want to [achieve a goal], so that [meaningful benefit].

## Context
[Brief current problem, reason for the change, or supporting evidence.]

## Acceptance criteria
- [Observable behavior or business rule.]
- [Relevant boundary or failure behavior.]

## Examples
[Named Given/When/Then scenarios for rules that benefit from examples.]

## Constraints / out of scope
[Known constraints, dependencies, and meaningful scope boundaries.]

## Open questions
[Unresolved decisions that affect behavior or scope.]

## References
[Relevant designs, evidence, related work, or technical discussion.]
```

The story captures who, what, and why. Use a real benefit rather than repeating the feature. Natural phrasing is acceptable when clearer than the sentence template. Keep implementation plans separate from the user goal; include necessary technical constraints without prematurely prescribing a solution.

## Acceptance rules and BDD examples

- Write acceptance criteria as short, observable rules with an objective pass/fail interpretation. Cover relevant happy paths, boundaries, permissions, and failures in proportion to the feature; do not add speculative scope or a fixed quota of criteria.
- Retain general rules even when examples illustrate them. One concrete scenario does not fully specify a general rule.
- Add Given/When/Then scenarios when conditions, permissions, calculations, state changes, or edge cases need clarification. Simple stories can use bullets alone. Do not mechanically translate every bullet into repetitive Gherkin.
- Name each scenario by the behavior it illustrates. Given establishes context, When identifies the trigger, and Then states observable results. Use concrete values that clarify a rule; illustrative fixture values must not introduce new requirements.
- Describe domain behavior rather than click-by-click scripts, CSS selectors, API internals, or database assertions unless those details are themselves part of the requested contract. Prefer one meaningful trigger per scenario.
- Group examples under their relevant rules when that improves readability; use a scenario outline or a small table when only data varies.
- Treat BDD as collaborative discovery, formulation, and automation. Do not imply that writing Gherkin alone means the team practices BDD, or that scenarios are executable or tested before they have been connected to tests and run.
