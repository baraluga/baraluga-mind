  deployment, verification, and recovery. See `deployment/README.md`.

## Verified commands

For local development run `python3.12 scripts/dev.py setup` (Windows:
`py -3.12 scripts/dev.py setup`). This installs and verifies Git hooks.
Use `scripts/dev.py hooks` to diagnose missing hooks; do not bypass or remove
hooks to make a commit or push pass. Run `python3.12 scripts/dev.py check` for
all checks using the managed `.venv`. CI uses the direct commands below:

```bash
python -m pip install -r requirements-dev.txt
python -m ruff check .
python -m ruff format --check .
python -m pytest
```

`pytest` enforces a 20% coverage floor for
`callbacks.py` and `data/real_data.py`. Preserve that gate and add focused
tests for deliberate behavior changes.

## Change discipline

- Commit messages must follow Conventional Commits. Follow the format and
  examples in [CONTRIBUTING.md](CONTRIBUTING.md#commit-and-push); omit scopes
  unless the user explicitly requests one. Keep each commit focused on one
  logical change, including its relevant tests.
- Preserve data semantics, especially labels, units, periods, ownership,
  committed-versus-realized categories, and workbook sheet meanings.
- Do not rewrite or reformat unrelated files. Review the final diff and keep
  generated data, reports, credentials, and other environment-owned artifacts
  out of Git.
- For notebook or pipeline edits, preserve notebook metadata and outputs when
  possible, inspect the changed cells, and add a narrow regression test when a
  behavior or schema assumption changes.
- The app can use tracked sample data, but real refresh inputs under
  `data_pipeline/inbox/` and `data/raw/` are ignored and environment-owned.
  Do not invent missing inputs or run a publish step to work around them.

## Deployment boundary

`main` is the development branch. Pushes and pull requests validate only.
Deployment requires manual workflow dispatch with an explicit `dev` or `prod`
environment. Dispatch defaults to dry run: backup, preparation and candidate
smoke checks still run, but deployment and rollback require the explicit
`deploy_after_validation` input. An always-run summary reports collected stages
and failed checks without raw business data. Dry-run success does not prove
rollout or browser behavior. Do not dispatch a release as part of a routine commit/push.
PROD's real service identity/CDH binding and runtime target remain unverified.

`code-and-data` uses the selected Git revision; `data-only` must preserve the
exact deployed code. Both collect all paired monthly CSV stages from the target's
CDH data bucket, then convert to the existing Excel runtime format. No date selector
or separate workbook upload is used. Require one CSV per `YYYY-MM` stage in both
masterupstream and masterdownstream; reject ambiguous or incomplete stages. Never
infer a month from a daily stage or rewrite business reference dates. Record source
and output hashes; smoke every pair before writing. Do not invent missing inputs
or silently use sample data.

Deployment uses the target's service client with `api.cdh` and verifies the
returned AWS identity. Keep recovery files private on the internal runner;
never upload workbooks or credentials as GitHub artifacts. Use the same bound
backup and candidate for rollback. Do not bypass hooks, smoke gates, target
checks, or the environment's deployment lock.

For the normal solo edit/format/lint/test/commit/push workflow, see
`CONTRIBUTING.md`.

## Cross-Repo Workflow: Porting A Script To A DAG

1. Run and observe the source script in `scraper-scripts`; capture inputs, outputs, credentials, file names, date logic, and failure behavior.
2. Choose the DAG repo by market ownership: `smp-india` or `smp-japan`.
3. Check whether an existing DAG for the same source should be extended before creating a new DAG.
4. Implement under `dags/src/`, keeping task runtime scraper modules under `dags/src/scripts/`.
5. Validate locally with `ruff`, `pytest`, and, when practical, `airflow dags test`.
6. Coordinate deployment through the appropriate branch/environment and `smp-tool` git-sync/Helm configuration.
7. Update `smp-dashboard` only after the DAG output is stable and visible where CDH/Grafana expects it.

# Parallel When Useful

For the task where this skill is invoked, explicitly use subagents if and only if the criteria below are met. Invocation authorizes that decision without another confirmation; it does not require delegation or expand the user's task or permissions.

## Decide whether to delegate

Delegate only when all of these are true:

- There is a concrete, bounded subtask with a clear deliverable that can run independently.
- The main agent has useful work to do alongside it, rather than immediately waiting for its result.
- The expected time savings or improvement in quality outweigh briefing, coordination, and review costs.
- Responsibilities can be separated to avoid conflicting edits and unnecessary duplicate work.

Good candidates include investigating independent components, comparing distinct approaches, or requesting a focused second opinion while continuing implementation or validation. An independent review may intentionally overlap in subject matter when a second assessment adds value.

Stay solo for small changes, tightly sequential work, or subtasks that require nearly continuous shared context. Using zero subagents is a valid outcome. Do not split work just to demonstrate delegation.

## Delegate with clear ownership

Use the available subagent tools within the current task. This skill does not request separate sidebar tasks. Choose the smallest useful number of agents within available limits.

Brief each agent with its objective, necessary context, permitted scope, expected result, and any file ownership boundaries. Keep integration and the final response with the main agent, and continue useful local work while agents run.

Review returned findings and changes before relying on them, reconcile disagreements, and perform verification appropriate to the combined result. End or redirect delegated work when it becomes redundant or no longer helps. Explain delegation briefly when it matters to the user's understanding; do not add a ceremony for deciding to stay solo.
