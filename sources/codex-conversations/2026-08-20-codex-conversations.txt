# Airflow Feature Spike — Top 5

## Scope

SMP already runs the latest Airflow release, 3.3.0. This is not an upgrade proposal or an exhaustive plugin catalogue. The goal is to identify five practical improvements based on end-user value and developer experience. [Airflow 3.3 release notes](https://airflow.apache.org/docs/apache-airflow/stable/release_notes.html)

## Baseline

India’s DAGs are mostly independent. Japan has substantially more cross-DAG orchestration, including 21 explicit DAG triggers and a large HJKS orchestrator. Neither market currently uses Airflow Assets.

Both deployments already have Celery workers, triggerers, StatsD, Okta authentication, Teams failure alerts, and some parameterised/manual workflows.

| Feature | Description | What it offers | Risk if not adopted |
|---|---|---|---|
| [Airflow Assets](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/asset-scheduling.html) | Models published data as a first-class dependency. | **End users:** clearer data readiness and dependencies. **Developers:** downstream DAGs react to successful publication instead of being hard-wired into orchestrators. Strong fit for Japan; lower immediate value for India. Source scrapers should remain cron-based. | Japan’s orchestration stays increasingly coupled and harder to follow as consumers are added. Low risk for India today. |
| [Deadline alerts](https://airflow.apache.org/docs/apache-airflow/stable/howto/deadline-alerts.html) | Alerts when a DAG misses an expected completion time—not only when it fails. | **End users:** earlier notice that data is late. **Developers:** one Airflow-native freshness rule instead of custom monitoring. Pilot first because the feature remains experimental. | Late-but-running jobs remain invisible until someone notices or the run fails. If no delivery expectation exists, there is little risk. |
| [Self-service runs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/params.html) | Standardises validated Params and Airflow’s built-in Backfill UI for repairs and reruns. | **End users:** approved operators can perform bounded repairs through a form. **Developers:** less repetitive operational support and fewer one-off manual patterns. | Routine recovery remains inconsistent and developer-assisted. This is friction, not an outage risk. |
| [Exception-aware retry policies](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html) | Airflow 3.3 can retry based on the actual exception rather than treating every failure the same. | **End users:** faster recovery from temporary source failures. **Developers:** transient errors retry; permanent authentication or configuration errors fail immediately; shared policies replace scattered retry logic. | Existing fixed retries remain workable but may waste time and duplicate logic. |
| [Versioned Git DAG bundles](https://airflow.apache.org/docs/apache-airflow/stable/administration-and-deployment/dag-bundles.html) | Pins each DAG run to the Git version that started it. | **End users:** fewer deployment-time inconsistencies. **Developers:** exact answer to “which code ran?” and reproducible historical failures. | Rare mid-run inconsistencies and harder historical debugging continue. This is platform hardening, not an urgent fix. |

## Recommendation

Start with a QA proof using **Japan OCCTO daily capacity → reconciliation**:

1. Keep the existing trigger during the proof.
2. Emit an Asset only after successful publication.
3. Add an asset-scheduled reconciliation consumer.
4. Compare behaviour before replacing anything.

This is small enough to demonstrate properly and representative enough to prove whether Assets can simplify Japan’s larger orchestration chains.
