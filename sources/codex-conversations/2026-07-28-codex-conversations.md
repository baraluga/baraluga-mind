GitHub doesn’t provide a repository-controlled prompt during `git clone`. Although Git has a `post-checkout` hook that runs after cloning, hooks are local configuration and aren’t downloaded from the repository—intentionally, for security. A company-managed Git configuration or custom clone wrapper could install one, but ordinary `git clone` would bypass it. [Git hooks documentation](https://git-scm.com/docs/githooks)

For your case, I’d use a layered approach:

1. Put a native warning at the very top of `README.md`:

```md
> [!WARNING]
> **CD pipeline migration is still pending.**
>
> This repository is ready for development, but deployments are not yet supported.
> Before attempting a deployment, please contact the Migration Team: [team/contact link].
```

GitHub renders this as a prominent colored alert, and the README is automatically displayed on the repository’s main page. [GitHub README documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)

2. Prefix the repository description:

```text
🚧 CD MIGRATION PENDING — development OK; contact the Migration Team before deploying
```

This stays visible near the top even when someone isn’t reading the README.

3. Add an organization custom property such as:

```yaml
cd_migration_status: pending
```

This gives you a searchable, machine-readable inventory of affected repositories and can later target organization rulesets or automation. [GitHub custom properties](https://docs.github.com/en/organizations/managing-organization-settings/managing-custom-properties-for-repositories-in-your-organization)

4. Most importantly, guard the actual production deployment. Configure the GitHub Actions production environment to require Migration Team approval, or make the deployment workflow stop with:

```text
Deployment blocked: CD pipeline migration is still pending.
Contact the Migration Team.
```

GitHub environments can require approval and restrict deployment access, so someone missing the banner still can’t accidentally deploy through the unfinished path. [GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments)

My recommendation: use the README warning plus repository description for visibility, and an environment protection rule for enforcement. The clone-time prompt is technically possible only if you centrally control developers’ Git setup, and probably isn’t worth relying on.

### Why arbitrary conversion doesn’t work

A notebook contains ordered cells executing inside one long-lived kernel. Cells can silently depend on:

- Variables created by previously executed cells.
- Cells being run in a different order from their displayed order.
- Local files and installed packages.
- Mutable in-memory dataframes.
- Interactive input and display state.

Airflow tasks are isolated units that may run in different processes or Kubernetes pods. They need explicit dependencies, persisted inputs and outputs, retries, timeouts, schedules, credentials, resource limits, and deterministic behaviour. Airflow’s own model defines a DAG separately from the work inside its tasks; the DAG controls task topology and operational behaviour. [Airflow DAG concepts](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html)

So cell 2 cannot simply use the dataframe from cell 1 after they become separate Airflow tasks. Cell 1 would need to persist it somewhere, and cell 2 would need to reload it.
