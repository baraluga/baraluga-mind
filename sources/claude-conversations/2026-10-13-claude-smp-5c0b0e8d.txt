## 14:09 assistant (smp-india/dags/src/scripts/khaba_generation_tsdb)

The two DAGs check the same S3 file (today's Khaba CSV, IST date). The difference is what each one does when the file isn't there yet.

| | **realtime** (`*/10`) | **minute** (`*/5`) |
|---|---|---|
| Check task | Plain `@task`, no retries | `task.sensor` in `mode="reschedule"`, `retries=0` |
| File missing | Within the day-transition window after midnight it **skips**. Otherwise it **fails at once** with `AirflowFailException`. | Returns "pending" (`missing_is_pending=True`) and keeps checking |
| Wait loop | None. The next scheduled run 10 min later is the "retry". | Checks every 5 min, backing off to every 15 min, for up to **`timeout=6h`** |
| Which date | From `data_interval_end` | From `datetime.now()`, so a run that waits past midnight switches to the new day's file |
| Effect of `max_active_runs=1` | Each run is short, so nothing piles up | One waiting run **blocks every later `*/5` run for up to 6h** |

Code: [india_khaba_generation_realtime_dag.py](smp-india/dags/src/india/india_khaba_generation_realtime_dag.py), [india_khaba_generation_minute_dag.py:59-68](smp-india/dags/src/india/india_khaba_generation_minute_dag.py:59), [khaba_generation.py:468-487](smp-india/dags/src/scripts/khaba_generation_tsdb/khaba_generation.py:468).

**What this means for Francois's two observations:** they are the same problem. Today's file isn't in the bucket.
- **Realtime "fails cleanly":** it finds no file, and every 10-min run fails right away.
- **Minute "weird state for 6 hours":** it finds no file, the sensor keeps waiting, and after 21600s it fails with `AirflowSensorTimeout`. Because `max_active_runs=1`, nothing else runs during that time. That's the ~6h bar in his chart.

## 14:10 assistant (smp-india/dags/src/scripts/khaba_generation_tsdb)

**Realtime's approach is better.** Make it fail fast and skip only during a short window after midnight.

The file is a live daily file that gets rewritten all day. Outside the first few minutes after midnight, a missing file doesn't mean "not there yet". It means the upstream process is broken, and waiting won't fix that. The minute DAG's 6h sensor treats an outage as a delay, and that causes three problems:

- **You find out late.** The first alert comes about 6h after the problem starts.
- **Nothing else runs.** With `max_active_runs=1`, all the `*/5` runs queue up behind the waiting one. When the file comes back, recovery waits for that run's next check, which can be up to 15 min after backoff.
- **It's hard to read.** Francois saw the 6h bar and couldn't tell what was going on, which is why he asked.

Realtime's fail-fast has one real downside: **alert spam**. Each failed run fires `on_failure_callback` to Teams, so a full-day outage means about 144 alerts. That's a problem with how alerts are sent, not with the check itself. Fix it on the alert side, for example by alerting only on the first failure in a row.

The smallest fix for the minute DAG is to keep the sensor and set `timeout` to about 15–30 min. That keeps the midnight grace period, and in practice it behaves like realtime. It's a one-line change. Want me to make it?

Yes, the reasoning is written down. You made this change yourself in commit `39a0aeb` on 2026-09-18 ("fix: back off while Khaba realtime source is missing"), one day after the minute DAG first shipped in `c5dfdd1`. The explanation is in [docs/bulk-backfill.md:100-124](docs/bulk-backfill.md:100), under "Realtime source outages".

**What the minute DAG did before that commit:** it worked exactly like realtime does today. It failed fast, skipped during the window just after midnight, and fired an alert every 5 minutes while the file was missing.

**Why it was changed, according to the doc:**
1. **To cut alert spam (the main reason).** The doc says a 6-hour timeout fails the run "instead of failing every five minutes while the file is missing". That's at most 4 alerts a day instead of about 288.
2. **To avoid holding a worker slot.** Reschedule mode frees the slot between checks, which matters on airflow-dev with only 4 slots.
3. **To handle runs that cross midnight.** Using `datetime.now()` means a wait that runs past midnight picks up the new day's file.
4. **To limit what counts as "pending".** Only a 404 is treated as missing data. A 403 or 500 still fails right away, and reconciliation and backfill runs still fail fast.

**What the doc doesn't explain:**
- **Why 6 hours.** No reason is given for that number specifically.
- **The cost of the hang.** It doesn't mention that one waiting run blocks every later run, or that you hear about an outage about 6 hours late. That's the "weird state" Francois noticed.
- **Where it's written.** The note is in `bulk-backfill.md`, not [docs/khaba-minute-feed.md](docs/khaba-minute-feed.md), which is probably why nobody found it.

**This changes what I said earlier.** The sensor was a deliberate fix for alert spam, not an oversight. Cutting the timeout to 30 minutes brings back some of that spam: 48 alerts a day during a full-day outage instead of 4. The real trade-off is how fast you hear about an outage versus how many alerts you get. If Francois cares most about hearing early, 30–60 minutes is reasonable. If not, the current design works as intended, and the reply to him is "it's waiting on the missing file by design".
