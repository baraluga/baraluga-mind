## 10:25 assistant (smp-tool)

The split is deliberate. It was decided on 2026-10-13 in SCR-1283, after both alternatives were tried.

**How they relate:**
- **The collector code (smp-india)** is generic. It knows nothing about sites. At startup it reads a `DARWIN_ENTITY_TAGS_JSON` environment variable that says which entities and tags to poll, and polls exactly those.
- **The deployment (smp-tool)** decides what goes in that variable. `sites.json` lists every known site and its entities, `enabled_sites.json` picks which ones each environment collects, and `render_darwin.py` combines them into the variable when it builds the Kubernetes manifest.

So "which sites" is treated like any other deployment setting (image tag, proxy, secret names), not like code. That's the same split as Airflow: smp-india holds the DAG code, and smp-tool holds the Helm values and cluster config. Michael, as cluster owner, expects it that way.

**Why the deployment didn't move into smp-india** (from my notes on SCR-1283):
- For smp-tool to read smp-india, it would need a personal token. Deploy keys are disabled in qrm-dms, and fine-grained tokens need owner approval.
- Deploying from smp-india would duplicate smp-tool's cluster config and need new EKS permissions.

**What it costs, and I think this is what feels off:** adding a site touches both repos, in a fixed order.
1. **smp-india first:** add the site's TSDB destinations to `mappings.json`, so the publisher knows where to write. Khaba's was `8bae384`.
2. **smp-tool second:** add the site to `enabled_sites.json` and redeploy. Khaba's was `9b9b914`.

If the order is reversed, the publisher receives data it has no mapping for and quarantines it. The collector README calls that out ("install and validate each site's publisher mappings before enabling collection"). Nothing enforces the order; it's a convention.

The freshness DAG follows this split: it checks what the collector actually collected (the state file), filtered by what the publisher maps. That's why a site enabled in smp-tool but never deployed, like Khaba right now, isn't flagged.

If the two-repo step becomes a real nuisance as more sites are added, it's worth raising with the team. But the reasons for the split still hold, so I wouldn't change it now.
