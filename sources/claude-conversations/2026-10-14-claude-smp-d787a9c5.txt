## 13:54 assistant (smp-common)

Mostly yes. `save_to_parquet` in smp-common turns every datetime column into a `"YYYY-MM-DD HH:MM:SS"` string when it writes the file, because Athena/Trino can't read nanosecond parquet timestamps. Here's what each date column would hold:

| Column | Format in the file | Timezone |
|---|---|---|
| `application_date` | `2026-10-14 18:30:00` | UTC |
| `publication_date` | `2026-10-13 11:30:54` | UTC |
| `ts` | `2026-10-14 18:30:00` | UTC, a copy of `application_date` for dashboards |
| `delivery_date` | `2026-10-15` | **IST** calendar date, the one exception |
| `as_of_date` | added by `save_to_parquet` | — |

Two things to watch:
- **The strings carry no `Z` or `+00:00`.** You can only tell they're UTC by convention, so a Grafana query needs to treat them as UTC, or the panel should be set to UTC, or the times will be shifted.
- **`delivery_date` is in IST on purpose.** An Indian delivery day runs from 18:30 UTC the previous evening, so filtering on this column gives whole Indian days. The REC dataset uses the same column.

I'd keep this exactly as the other India datasets do it, so whoever builds the real dashboard sees the same columns in every dataset. I haven't checked how `as_of_date` is formatted.

## 13:54 assistant (smp-common)

"Long format" means each row holds one value: one series at one timestamp. So the two series are stacked on top of each other rather than side by side:

| application_date | series_name | value |
|---|---|---|
| 2026-10-14 18:30:00 | NOC WRLDC Khavda | 199.99 |
| 2026-10-14 18:30:00 | NOC NRLDC Khaba | 200.0 |
| 2026-10-14 18:45:00 | NOC WRLDC Khavda | 199.99 |
| 2026-10-14 18:45:00 | NOC NRLDC Khaba | 0.1 |

That's 2 rows per 15-minute slot, about 4,000 rows in total today.

**"Wide format"** is the other option: one row per timestamp, with a column for each series:

| application_date | noc_wrldc_khavda | noc_nrldc_khaba |
|---|---|---|
| 2026-10-14 18:30:00 | 199.99 | 200.0 |
| 2026-10-14 18:45:00 | 199.99 | 0.1 |

**How they compare:**

| | Long | Wide |
|---|---|---|
| Grafana query | `SELECT ts, series_name, value`, and Grafana draws one line per `series_name` | `SELECT ts, noc_wrldc_khavda, noc_nrldc_khaba`, one line per column, no extra setup |
| Adding a third series later | Add it to the list of series the DAG reads; the table doesn't change | New column, which means a schema change and updating the CDH registration |
| Per-series details (`publication_date`, `series_id`) | One column each, filled in on every row | Need a column per series (`khavda_publication_date`, …) |
| Matches existing India datasets | Yes (REC, Khavda) | No |

Wide is slightly easier for a dashboard with exactly these two series. Long handles change better and matches what's already there, which is why I'd go with long.
