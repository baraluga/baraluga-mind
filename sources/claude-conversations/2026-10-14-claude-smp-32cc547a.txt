The difference between an every-minute scheduled DAG and the @continuous timetable comes down to how the work is triggered and managed by the Airflow scheduler.
While both patterns can result in tasks running back-to-back, they impact your system's performance, database, and infrastructure in fundamentally opposite ways.

Direct Comparison


Feature	Every Minute Scheduled (* * * * *)	Continuous Loop (schedule="@continuous")
How it's triggered	The scheduler forces a new DAG Run into existence every 60 seconds based on the clock.	The scheduler starts a new run only after the previous run finishes successfully.
Database Overhead	Extremely High. Generates 1,440 discrete DAG runs and task logs every single day.	Extremely Low. Only processes one active run record at a time.
Task Overlap Risk	High. If a task takes 65 seconds, the next minute's run will spin up anyway, causing stacking and resource exhaustion.	Zero. Built-in sequential execution guarantees tasks can never overlap.
Kubernetes Impact	Constantly creates, runs, and destroys pods every 60 seconds (massive API churn).	Smoothly transitions from one pod lifecycle to the next without stacking pressure.


Deep Dive: How They Act Under the Hood


1. Every Minute Cron (* * * * *)

This is an unconditional time trigger. Airflow doesn't care if your previous execution is still running, stuck, or struggling. When the clock hits the next minute, it creates a brand new DagRun row in your database and attempts to queue its tasks.
If your Kubernetes cluster experiences a brief slowdown and a task takes 2 minutes to complete, Airflow will pile up two more runs behind it. This creates a cascading bottleneck that can easily freeze your scheduler or overwhelm your IEX API rate limits.

2. The @continuous Schedule

Think of @continuous as a self-perpetuating loop managed by Airflow.
When you set schedule="@continuous" alongside max_active_runs=1, Airflow treats the DAG like a persistent background worker daemon. The scheduler kicks off Run #1. Run #1 calls the IEX API, processes the data, and finishes. The instant the scheduler marks Run #1 as successful, it immediately triggers Run #2.
If a network hiccup causes Run #1 to take 3 minutes, Airflow simply waits. No new runs are queued, no extra pods are spawned, and no database bloat occurs. It natively adapts to the speed of your infrastructure and the external API.

Summary

• Use Every Minute Scheduled if you want to stress-test your database and don't care about overlapping tasks (not recommended).
• Use @continuous if you want near-real-time data ingestion in Airflow without breaking your Kubernetes cluster or your metadata database.
