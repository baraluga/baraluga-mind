## 15:21 assistant (smp-india)

I wouldn't add end-to-end tests for every DAG. The unit tests leave a real gap, but full e2e coverage would mostly not catch the problems this repo has actually had.

**What the DAG unit tests cover today.** The 17 non-Darwin test files build the DAG, check its settings (schedule, retries, catchup), and call each task's `python_callable` on its own with mocks. See [test_india_iex_rec_tsdb_dag.py](smp-india/dags/test/test_india_iex_rec_tsdb_dag.py). None of them runs `dag.test()`, so these never get exercised:
- data passed between tasks (XCom), and the shapes one task returns to the next;
- trigger rules and task order, such as the `ALL_DONE` upload problem we hit in scraper-dags;
- the real Airflow runtime context and the output paths it produces.

A run-the-whole-DAG test would catch that kind of bug cheaply.

**What has actually gone wrong recently.** The REC scraper stopped being scheduled while its TSDB data went stale, the Khaba CSV changed layout and shifted its columns, and the CDH crawler prefix was wrong. All three were changes or misconfiguration in something outside our code. An e2e test with fakes would have passed in every case, because the fakes behave the way we assume the real systems do. Those failures get caught by freshness monitoring (like the SCR-1268 Darwin freshness DAG) and by contract tests built on real recorded responses.

**What's stopping us is cost, not anything technical.** Darwin's e2e harness was cheap because Darwin already had a fixture contract and a SQLite fake TSDB. Each other DAG would need a fake for every external system it touches: the IEX/HPX APIs, TSDB reads and writes, and uploads to S3, CDH or SharePoint. Every run also needs its own process, because Airflow reads its config once per process (the reason `test_darwin_poc_airflow.py` starts a subprocess). That's roughly 20 DAGs' worth of fakes to build and keep current. As practice it's fine. As coverage it's a poor return.

**What I'd do instead:**
1. **A spike on one high-risk DAG.** `india_khaba_generation_realtime_dag` is the candidate: it chains several tasks, and its forecasts only reach Grafana inside the actuals file. Generalise the Airflow harness into a fixture, patch only the outside boundaries, and run `dag.test()`. That shows the real cost per DAG before anyone commits to more.
2. **Contract tests built on recorded real responses** for the sources that have already drifted (Khaba CSV, IEX), so a format change fails a test instead of reaching prod.
3. **Leave the rest on unit tests and freshness alerts.**

If the spike turns out cheap, extending it to the IEX RTM and Khaba reconciliation DAGs is next. I'd stop there.
