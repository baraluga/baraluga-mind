**Yep—SCR-1273 is technically feasible, with substantial reuse from Tuticorin.** It needs some generalisation and source validation, rather than another ingestion pipeline.

I read [SCR-1273](https://tractebel-et.atlassian.net/browse/SCR-1273), the **“(scr-1261) Darwin API Realtime”** chat, and the current code. Tuticorin is at the real-collector deployment handover stage; cluster verification and live TSDB publication/read-back are still outstanding in that chat.

The requested rollout is:

| Priority | Site | Measurements |
|---|---|---|
| 1 | Khavda — INKHA | Power, global irradiance, tilted irradiance, module temperature |
| 2 | Sharpar — INGU2 | Same four |
| 3 | Raganesda — INRAG | Same four |
| 4 | Titwha — INGUV | Power, wind direction, wind speed |

That is **15 measurement streams, potentially 30 TSDB destinations** if every measurement needs both resolutions. Mateo still needs to supply the IDs.

The existing foundation already covers continuous collection, durable storage, five-minute Airflow publication, unit conversion, minute outputs, 15-minute averages, retries and TSDB read-back. The [output mapping model](./smp-india/dags/src/scripts/darwin_publish/aggregation.py:33) supports both resolutions for any mapped measurement.

**The things to resolve before calling it ready:**

- **Plant access and source mappings.** The prior live checks proved access to the two Tuticorin entities only. We still need to verify these four plants’ actual Darwin entity codes, tags, units and update frequency. The ticket’s site codes alone do not establish the API mappings.
- **Mixed solar and wind configuration.** The collector currently applies one tag list to every configured entity. We should support tags per entity, or use separately configured collectors with separate storage. Otherwise solar plants would repeatedly be queried for wind measurements and vice versa.
- **What “1m granularity” means.** Current collection retains the first valid observation captured for each source minute, preserving its exact timestamp. It is an instantaneous sample, not a one-minute average. That needs to match the intended requirement.
- **Quarter-hour timing and missing data.** The [current aggregation](./smp-india/dags/src/scripts/darwin_publish/aggregation.py:303) requires all 15 minute samples and waits five minutes after the interval closes. For example, a 10:00–10:15 window becomes eligible at 10:20. Missing minutes prevent publication of that average. Confirm whether SCR-1273 accepts this delay and completeness rule.
- **Wind direction averaging.** Reuse the existing circular mean: 359° and 1° should average around 0°, not 180°.

**One particular Khavda check:** we already have a [Khaba CSV feed](./smp-india/docs/khaba-minute-feed.md) publishing overlapping measurements at both resolutions. Confirm whether INKHA is replacing that source or adding separate Darwin series. Reusing its TSDB IDs would require a controlled cutover, including the reconciliation writer.

My recommendation is to **start read-only Khavda discovery while Tuticorin deployment finishes**, then onboard Khavda through the verified pipeline before extending to the other three. I’d classify this as **moderate incremental work**, conditional on source access and compatible data—not just adding four names to configuration.

This assessment is based on the ticket, chat and code; I haven’t live-tested the four new plants or changed anything.

why are we setting the max files to 200 again? And from what value? 100?

## 11:58 assistant

Short answer: the code default is **100** (`DARWIN_PUBLISH_MAX_FILES` in `settings.py`). The 200 was my precaution, not something we measured. I haven't checked what's set in dev Airflow, so it's 100 unless someone already set the Variable.

**What the limit controls:** each publisher run takes at most that many pending JSON batches. The collector writes one batch per entity response page that has newly accepted samples. Anything over the limit waits for the next 5-minute run.

**Why I proposed 200:**
- **Volume went up:** yesterday's live run wrote 26 batches in 150 s for the six entities, about 10 a minute. That's roughly 50 files per 5-minute run, against about 8 for Tuticorin alone. At a limit of 100 that's 2× headroom, and at 200 it's 4×.
- **Backlog after downtime:** if Airflow is paused for an hour, 100 means several runs to catch up. A backlog bigger than the limit also delays the 15-minute averages. In the paginated test, averages aren't finalized until a run has consumed its whole snapshot.
- **The cost of a higher limit:** each run does more work inside the 4-minute task timeout. The local test was well under a second, but that wasn't real EFS or TSDB latency.

**Is it necessary?** At steady state, 100 probably copes with ~50 files per run. If you'd rather not change a Variable until it's needed, we could leave it at 100 and watch for a growing backlog. The change is trivial to make later, and it's an Airflow Variable edit, not code.

My lean is still 200 for the first rollout, so a hiccup doesn't snowball, and then tune it down after we've seen real run times. But it's your call.
