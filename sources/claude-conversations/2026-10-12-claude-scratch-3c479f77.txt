Yes, it works on webapps. REA has a set of browser tools, and they come at a webapp from three directions:

**1. Static: the shipped JS bundle**
- `analyze_web_bundle` and `export_web_scripts` pull the minified bundles and inspect them.
- `recover_javascript_sources` rebuilds the original source when the site ships source maps.
- `trace_web_module_imports` and `trace_web_source_location` follow modules and map bundle locations back to source lines.
- `compare_bundles` and `compare_source_to_bundle` diff two deploys, or your source against what's actually deployed.

**2. Runtime: a page you already have open**
- It attaches to a browser you started yourself, through a local Chrome DevTools debugging port (Chrome launched with `--remote-debugging-port=9222`).
- `list_browser_targets` lists the open pages. Then `inspect_web_page`, `inspect_web_event_listeners`, `observe_web_session`, `observe_web_execution` and `capture_web_screenshot` look at the selected page.
- It only watches. It won't click, navigate or run code in the page, so you drive the app while it records.
- Cookies, auth headers, storage values and request/response bodies are left out of captures on purpose.

**3. Recorded traffic**
- `inspect_web_network_capture` reads a HAR file (exported from browser DevTools) or a mitmproxy capture you made earlier, without re-fetching any URL.
- `compare_web_captures` diffs two captures.

**Tying it together:** `reconcile_javascript_runtime` matches what the static analysis found against what was seen at runtime. One limit: seeing a bundle load doesn't prove every module inside it ran.

**What it can't see:** server-side code. You only get what reaches the browser: the client bundle, network traffic, the DOM and console output.

I've traced how sync-control works. The short version: YNAB's web app keeps its own copy of your budget in the browser, and every so often swaps "what's changed since we last talked" with the server, using a running change counter on each side to know what to send.

## How it fits together

```
sync-control (Ember service, ~30 lines)
  └─ applicationService.syncManager       ← created when the app starts
       └─ shared library ("defaultInstance")
            ├─ entityManager   (fires an event when a record is created or edited)
            ├─ store           (works out what changed, does the sync)
            └─ apiAdapter.v1   → POST /api/v1/catalog
```

**1. sync-control is just a pause button.** It has suspend, resume, start, stop and sync-now. Suspend waits for any sync in progress, sends your unsaved edits, then turns on a read-only flag in the shared library. Resume turns read-only off and restarts automatic syncing if it was running before.

**2. The real engine is a separate shared library.** Two clues:
- Its code is written differently from the Ember app's own code (it looks like compiled TypeScript).
- It's created with `deviceOS: "web"`, which suggests the same library also runs on other platforms.

Next to it in the same file there's a lot of code compiled from Kotlin (the language), including class names like `persistence.catalog.userbudget.UserBudgetServer`. My guess is that YNAB shares data-layer code across web and mobile. That's an inference from how the code looks; I haven't confirmed it.

**3. When it syncs:**
- **When you edit something:** creating or changing a record triggers a sync after a very short wait (`timeToWaitAfterChangeToPushChanges` is 10, probably milliseconds).
- **On a timer:** it also syncs on a regular "heartbeat". The built-in default is every 60 seconds, but your page sets `AUTO_SYNC_RATE` to **180000**, so in practice it's **every 3 minutes**.
- **When the connection drops:** a 503 error, status 0 (no response) or a timeout marks the app as Disconnected. After a failed sync while disconnected, it retries after 2 seconds.

**4. One request carries everything.** Your budget, user-level ("catalog") data and family data all sync through a single endpoint, `POST /api/v1/catalog`. The body is `{operation_name, request_data}`, where the operation is `syncBudgetData`, `syncCatalogData` or `syncFamilyData`. Login, logout and password reset go through the same endpoint. Version 2 of the API (`/api/v2/user` and so on) is a normal REST API used for other things.

**5. Change counters decide what gets sent.** Each budget sync sends:
```
budget_version_id, sync_type (Delta | Backfill),
starting_device_knowledge, ending_device_knowledge,
device_knowledge_of_server, schema_version, schema_version_of_knowledge,
changed_entities: { be_accounts, be_transactions, be_payees,
                    be_subcategories, be_monthly_subcategory_budgets, ... }
```
- Your browser and the server each keep a running count of changes (called "knowledge").
- Each side tells the other "I've seen you up to change N", and the reply includes only records newer than that.
- A **Backfill** sync resets the counters to 0, which means "send me everything".
- Deleted records are kept and flagged (`is_tombstone`) rather than removed.

**6. Writes are blocked in read-only mode,** except for a sync request that has no outgoing changes. That's how suspend still lets server updates come in.

## Two things worth knowing

- **Local edits beat incoming changes for that round.** If you edit something while a delta sync is in flight, the server's incoming changes are thrown away, with the log line "Incoming changes from delta sync were ignored because we had new local changes." I assume a later sync picks them up again, but I didn't check that.
- **Every sync is checked against the server's schema version.** If the server answers in a schema version different from the one the client expects, the client errors out instead of trying to merge.
