Eric's right that Codespaces only runs on GitHub's machines; you can't host it yourself the way ENGIE hosts the Walnut runner for Actions. It's a real issue, though not an automatic deal-breaker.

**Why it matters**
- **ENGIE's own track record:** Walnut set up self-hosted runners because GitHub's machines couldn't reach internal systems like Artifactory and VPN-only services. Codespaces has exactly that problem, and there's no self-hosted way around it.
- **Our workaround is only partial:** a prebuilt image fixes dependency installs. But users still couldn't reach TSDB or other VPN-only systems from the IDE, so testing would only happen through the dev Airflow.
- **Security approval:** it's a new cloud environment where users run code and possibly handle credentials. Security may need to sign off.

**What softens it**
- The code is already on GitHub's cloud (`qrm-dms` is on GitHub Enterprise Cloud), so data location isn't a new concern.
- In the shared-sandbox model, real runs happen in the dev Airflow anyway. The IDE only edits and pushes.

**My read:** add this to the earlier signals (no Confluence page, no process, no replies in Builder Community), and Codespaces looks **unlikely to be approved in practice**, even if it might work technically.
