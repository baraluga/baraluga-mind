## 00:33 assistant (smp-dashboard)

The data itself is fine: every day so far has 96/96 DA and 96/96 ID rows, and the files are being written. The problem is how much load the run puts on TSDB, and you're right to be uneasy about it.

**What the log shows:**
- **Each read takes 8–10 seconds**, because the `last-version` endpoint runs an Athena query behind the scenes. The DAG does one read per series per day: 2 series × 9 days = 18 Athena queries, about 3 minutes per run, every 10 minutes.
- **The repeated 503s** ("Too many athena queries 2 are running for the current user concurrently") mean TSDB allows only 2 concurrent Athena queries per client. Our client, `2-s-scrapertool-service-application…`, is shared by every India DAG that reads TSDB. The SDK retries and recovers every time, so the run succeeds. But this DAG now competes with the Khavda DAG (27 reads per 10 minutes, same pattern), the Khaba DAGs and the IEX RTM reads, where SCR-1284 set a 5-minute latency target. It can slow those down.
- **Harmless noise:** `Okta configuration is missing` comes from an Airflow plugin and appears in every DAG's log. The long hex string is a token-cache key, not the secret.

**Proposed fix:** read each series once per run for the whole 9-day window instead of once per day. That's 9 × 96 = 864 rows per series, well under the row cap, so a run drops from 18 Athena queries to 2: about 9× less load, and runs finish in ~20 seconds instead of ~3 minutes. For backfills, the read gets split into 7-day chunks to stay under the cap (2 Sep → today is 7 chunks per series). The output files stay identical; only the read pattern changes.

Khavda has the same per-day read pattern. I'd leave it alone for now and offer it as a separate follow-up.

The DAG isn't failing, so it can keep running while I make the change; there's no need to pause it.
