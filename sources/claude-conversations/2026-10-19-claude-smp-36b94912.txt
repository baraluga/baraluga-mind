Feasible, and not complicated. It's the same file, just kept up to date. Here's how I understand it: besides "is the data fresh?", the freshness check should also answer "what state is the collector itself in?", so an alert says *why*, not just *what*.

**Design:** the collector maintains `collector-state/runtime.json`:
- **At startup:** image tag, environment, the streams it's configured to poll, and the start time.
- **After every poll cycle (every 15 s):** when it finished, how many observations it got, and which entities failed.

**Each freshness run then checks, in order:**

| Check | Alert text | Meaning |
|---|---|---|
| `runtime.json` missing | collector status missing | the running image predates this change (dev right now), or the wrong volume is mounted |
| Last poll too old | collector not polling: last poll *N* min ago | the collector is down or stuck |
| Expected stream not configured | SOF_INNS7: not configured in running collector `<image tag>` | a deploy problem: wrong or old image (today's Khaba case) |
| Entities failing in the last poll | SOF_INNS7: polling failed | a Darwin or access problem for that entity |
| Data stale (today's check) | newest source minute is *N* min old | the source isn't sending new data |

It also always logs the image tag and start time, so every run shows what's deployed, without kubectl.

**One rule I'd put in:** writing the status file must never crash the collector. Today a disk error in the collector deliberately stops the process, to protect the data. For this status file, a failed write is just logged, and collection continues. Otherwise monitoring could cause the very outage it's meant to detect. The "last poll" check reuses the existing 10-minute threshold, so there's no new Variable.

**Cost:** one small extra write to EFS every 15 seconds, and a few dozen lines across the collector, the check and the tests.
