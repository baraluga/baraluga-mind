## 11:12 assistant (smp-india)

The 49 minutes is almost entirely TSDB overhead. It's three things, and the codebase already has the fix for all three.

**Why it's slow**
1. **Every 15-minute run republishes everything.** That's 6 chains, today and tomorrow for DAM, GDAM and HPDAM, even when HPX returned exactly the same bytes as last time. After the daily publication, almost every poll is like that.
2. **Reads happen one series at a time.** Publish reads each series separately to find changed points, 14 serial reads for GDAM alone. Verify then reads them all again, even when nothing was written.
3. **Verification waits are expensive.** The TSDB applies writes asynchronously. If a readback isn't visible within about 20 seconds, the task fails and Airflow waits **5 minutes** before retrying, up to 6 times. That's why `verify_gdam_tomorrow` was on try 3 and `publish_gdam_tomorrow` on try 2. Once a run passes 15 minutes, `max_active_runs=1` queues the next one, which explains the 9-minute late start.

**The fix: reuse what the IEX RTM realtime DAG already does**
- **Skip the TSDB when the source hasn't changed.** Save the source SHA per market and date once a publish is confirmed. If the next poll gets the same bytes, skip the TSDB entirely. IEX stores this in an Airflow Variable, and I'd do the same here.
- **One bulk read instead of N serial reads.** Use `run_measured_batch(..., mode="bulk")` from `smp_common`. As a bonus, it logs `SMP_TSDB_TIMING` with per-run read and write seconds, so we'll finally see real numbers. Right now our own log suppression hides them.
- **Verify only if something was written,** and do it with a short in-task poll of a couple of minutes instead of failing and waiting 5 minutes. If publish finds no changes, its own read already proves the TSDB holds the values.

**Expected result:** most polls should take about a minute, since they only collect. A run that actually writes should take a few minutes, well under 15. RTM uses the same publication module, so it improves too. These figures are estimates and I haven't measured anything yet; the timing logs will show the real numbers after the change.

This changes how prod verifies data, and the "no-change means verified" step rests on behaviour I haven't checked live. So I'd write a short plan and run one read-only review on it before coding, then tests first.
