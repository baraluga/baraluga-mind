## 11:48 assistant

No, nothing moved. The REC scraper is still the same Lambda it always was, and the Airflow DAG is still the same DAG. We just turned the scraper back on and added alarms.

**How it works**
1. The **scraper** is a Lambda in apac-tsdb-scraper. It pulls REC from the IEX API every day and writes it to TSDB.
2. The **Airflow DAG** (`india_iex_rec_tsdb_dag`) reads REC from TSDB and publishes it to CDH, which is where Grafana reads it from.

**What broke**
Around 23 July, `iex_api_rec` was removed from the Lambda's list of scrapers to run (`SCRAPER_NAMES`), so the scraper just stopped. The DAG kept running green because it re-published the old July data from TSDB every day.

**What we did**
1. **Turned it back on:** added `iex_api_rec` back to that list. That was one setting change in prod, with no code deploy.
2. **Backfilled:** ran a one-off replay so TSDB got the 5 sessions it missed (29 Jul to 30 Sep). Then the DAG published them to CDH.
3. **Added alarms so this can't go silent again:**
   - The DAG now fails and alerts Teams if the newest REC data is over 25 days old, or missing. That would have flagged this in mid-August.
   - The DAG only publishes to CDH after a successful read, so it can't push stale or partial data.
   - A new command, `prod_scraper_ops.py check-active`, flags it when the Lambda's scraper list differs from the repo's config. You run it by hand after a deploy.

Steps 1 and 2 fixed the data. Step 3 is the "detect similar issues" part Francois asked for.
