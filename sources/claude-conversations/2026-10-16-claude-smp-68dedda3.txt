## 14:45 assistant (smp-india)

The writes now go through. What breaks is the **amount of reading per run.**

**Why it times out:** one run publishes the whole backlog at once: 1,783 points across about 15 series, spanning yesterday 09:47–16:01. For each series, the run reads TSDB **three times**:
1. A conflict pre-check in our publisher.
2. A "what actually changed" check in the shared `publish_batch`.
3. A read-back to verify the write. If the data isn't visible yet, this waits 10 seconds and retries, up to 6 times.

Yesterday's data comes from Athena, which allows **only 2 queries at a time on our shared account**, so most reads are refused and retried after several seconds. About 45 slow reads doesn't fit in 4 minutes. The timeout hit during verification.

**Is anything wrong?** No:
- No data is lost. Files are only deleted after verification succeeds.
- Writes are repeat-safe, and the next run's "what changed" check skips points that already landed. So it will creep forward, but slowly, with a failure and a Teams alert on most runs, while hogging the shared Athena slots.

**Proposed fix:** bound each run's work, so every run finishes and acknowledges something.
- **Publish at most N series per run, oldest first,** with N as an Airflow Variable (`DARWIN_PUBLISH_MAX_SERIES`, default about 5). The rest wait in the outbox for the next run, as they already do today.
  - **Backlog:** it drains over a few runs instead of failing forever.
  - **Steady state:** each series gets its turn within a few runs, carrying several minutes of points, so throughput keeps up and the delay stays around 15 minutes. Oldest-first means no series gets starved.
- **Raise the task timeout from 4 to 10 minutes.** `max_active_runs=1` already stops runs from overlapping, so a long run just delays the next one.
- **Leave the triple read alone for now.** Removing the overlap means touching the shared `publish_batch` that other DAGs use, so it's a separate change.

Your new review rule applies here: this changes how data gets verified, and it rests on Athena and DynamoDB timing I haven't measured. So before writing code, I'd run one read-only Codex review on this plan, then implement test-first.

okay, why the need for arbitrarily waiting for 30 seconds?

## 15:13 assistant (smp-india)

It's not a fixed wait. **30 seconds is a ceiling, not a pause.** Each series write returns the moment TSDB confirms it's stored. In the probe that took 8.6 seconds, so a normal run never waits anywhere near 30.

**Why have a limit at all:**
- **Storage confirmation is asynchronous.** The write goes into TSDB's intake queue, and TSDB reports "stored" a few seconds later. The SDK needs to know how long to wait for that report.
- **With no limit (`0`), the SDK doesn't ask for confirmation at all.** It's fire-and-forget, the unsafe mode we decided against.
- **Without a ceiling, a single stuck series could hang the whole run** until Airflow's 4-minute kill, at which point nothing gets acknowledged.

**Why 30 specifically:** it's a judgement call, not a measured number. It's about 3.5× the one write we timed, so normal variation passes, but a stuck series gives up after 30 seconds and the run moves on. The files for any unconfirmed series are kept and retried next run, so nothing is lost.

It does have an edge: if *every* series hit the 30-second ceiling, 18 × 30 seconds is about 9 minutes, past the 4-minute task limit. On a really slow UAT day, the run would time out and simply retry later. If the first real runs show confirmations reliably around 8–10 seconds, I'd lower it to about 15 seconds, which keeps even a bad run inside 4 minutes. I'd measure before tuning, though, since right now we have exactly one data point.
