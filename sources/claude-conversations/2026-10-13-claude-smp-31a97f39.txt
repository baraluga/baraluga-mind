## 10:55 assistant (smp-india)

You don't need any new code. The DAG already handles this case, the default grace period is just too short.

`check_khaba_source_exists` (`khaba_generation.py:470-487`) works like this when today's file is missing:

- **Inside a grace period after IST midnight**, the run is **skipped**. It doesn't count as a failure and doesn't alert on Teams.
- **After the grace period**, the run fails and alerts. That's the alert we want, because the file really is late.

The grace period comes from the Airflow Variable `KHABA_GENERATION_SOURCE_TRANSITION_WINDOW_MINUTES`, and **it defaults to 20 minutes** (`khaba_generation.py:23`). The file actually shows up about 4 hours after midnight. So the first ~20 minutes skip, and the remaining ~3h40 produce the ~24 failed runs you saw.

**My recommendation:** set that Variable in both QA and prod to the latest arrival time we've seen plus some margin. Something like `300` (5 hours) covers "about 4 hours". After that:

- Normal mornings show green and grey skipped runs, with no failures and no Teams noise.
- If the file still hasn't arrived after 5 hours, you get one real failure and an alert, so a genuine upstream outage still gets noticed.
- Data isn't affected. The realtime DAG only works on today's file, and the reconciliation DAG still fills in the end of the previous day.

If you'd rather have it tracked in git than as a hand-set Variable, change the default to 300. That's a one-line change plus its test.

I'd drop the "back off after 5 consecutive failures" idea for this. It slows the DAG down instead of telling apart "not yet" from "missing", and the grace period already does that.

Before you pick a number, check the actual arrival times. Looking at `LastModified` on the first object of each day in S3 over a couple of weeks will tell you if "~4h" is reliable. If it sometimes arrives at 6h, 300 will still produce a failure on those days. I haven't changed anything.
